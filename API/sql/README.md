# Database scripts

Run them in this order, inside the database the API uses (`DB_NAME` in `API/.env`):

| Script | What it does |
|---|---|
| `01_create_database.sql` | Drops and creates every table. **All data is lost.** |
| `02_seed_data.sql` | Minimal test data: 3 users (one per role) and 4 donors. |
| `03_demo_data.sql` | Large fictitious data set so every screen has something to show (see below). Optional. |
| `04_app_users.sql` | Least-privilege logins for the API and the daily task, so nothing connects as `sa` (see below). Run it again after `01_create_database.sql`. |
| `05_donor_notes_and_call_results.sql` | Only for a database created with an older `01_create_database.sql`: adds `Donor.Nickname`, `Email`, `OfficePhone`, `PhoneCall.CalledAt`, `ResultNotes` and the `DonorNote` table without losing data. Run `04_app_users.sql` again afterwards. |

None of them has `GO` separators or variables, so they run the same in both clients:

- **DBeaver:** open the file and use "Execute SQL Script" (Alt+X), not Ctrl+Enter.
- **sqlcmd:** `sqlcmd -S <host> -d <database> -U <user> -f 65001 -i API/sql/03_demo_data.sql` (`-f 65001` reads the file as UTF-8 so the accents are kept).

## App accounts (`04_app_users.sql`)

The API must never connect as `sa`: if the API (or its `.env`) is compromised, `sa` gives
control of the whole server. The script creates two SQL logins that can only do what the
code needs:

| Login | Used by | Can do |
|---|---|---|
| `caritas_api` | the API (`DB_USER`) | `SELECT` on the 8 tables; `INSERT` on `Donor`, `PhoneCall`, `Collection`, `DonorNote`, `Donation`; `UPDATE` only of `PhoneCall.Status`, `ResultNotes`, `CalledAt` and `Collection.Status`, `Notes`, `ScheduledDate`, `RouteOrder` |
| `caritas_tasks` | the daily task (`TASKS_DB_USER`) | `SELECT` on `RecurringDonation`, `PhoneCall`; `INSERT` on `PhoneCall`, `Collection`; `UPDATE` only of `RecurringDonation.NextInstallmentDate` and `Status` |

Neither can delete rows, change tables, read other databases or change server settings.
If the code starts using a new table or statement, add its `GRANT` to the script and run it again.

Steps (as `sa` or another sysadmin):

1. Generate two different passwords: `python3 -c "import secrets; print(secrets.token_urlsafe(24))"`.
2. Replace `REPLACE_WITH_API_PASSWORD` and `REPLACE_WITH_TASKS_PASSWORD` in the script
   **without saving the file** (or revert it afterwards) and run it in the API database with Alt+X.
   The last result lists the permissions of each role.
3. In `API/.env` on the server set `DB_USER=caritas_api`, `DB_PASSWORD=...`,
   `TASKS_DB_USER=caritas_tasks` and `TASKS_DB_PASSWORD=...`, and restrict the file:
   `chmod 600 API/.env`. Restart the API and check that it starts.

**Rotating a password** (for example every semester, or right away if it leaked):
`ALTER LOGIN caritas_api WITH PASSWORD = N'<new password>';`, update `API/.env` and restart the API.

**Hardening `sa`** once the API works with `caritas_api`:

- Do not use `sa` in DBeaver either: create a personal login per administrator and use that.
- Then disable `sa` (`ALTER LOGIN sa DISABLE;`), or at least give it a long new password.
  Check first that your personal login is `sysadmin`, or you will lock yourself out.
- Do not expose port 1433 to the internet: only the API server needs to reach it.

## Demo data (`03_demo_data.sql`)

Generated by `generate_demo_data.py` (fixed random seed, so the output is always the same).
Do not edit the SQL by hand: change the generator and run `python3 API/sql/generate_demo_data.py`.

What it inserts:

- 28 users: 4 admins, 10 telefonistas and 14 recolectores.
- 260 donors in the Monterrey metropolitan area with different histories: active monthly
  pledges (cash and transfer), occasional donors, finished, paused and cancelled pledges,
  donors who stopped giving (most of them `HIGH` risk) and prospects who never donated.
- About 1,400 calls, 560 collections and 790 donations spread over the last 10 months,
  so the monthly chart, the KPIs (including `atRiskDonors`) and the donor filters have data.
- Work for today: every telefonista has pending calls today (some already made) and in
  the next days, and every recolector has an ordered route (`RouteOrder`) today and tomorrow.

Dates are relative to the day the script runs. Running it again deletes its own rows
(its donors, found by phone, and its users, found by email, plus every call, collection,
pledge and donation that points to them) and inserts them again with the dates moved to
the new day. Rows created by `02_seed_data.sql` or by the apps are not touched.

It works after `01_create_database.sql` alone (it creates the roles if they are missing)
or after `02_seed_data.sql`.
